## Review Questions

**1. A colleague creates a subnet, names it public-subnet, tags it Tier=public, and turns on auto-assign public IPv4. Instances launched into it cannot reach the internet. Explain exactly what is missing, and explain why the name, the tag and the public IP address all failed to make it public.**

What is missing is a route. A subnet is only public because its route table has a 0.0.0.0/0 route pointing to an internet gateway, nothing else about it matters. The name is just text, the tag is just metadata, and an auto-assigned public IP just means the instance gets an address, it does not create a path for traffic to actually leave the VPC. I proved this myself in Step 13, my public and private subnets had identical route tables until I actually added the default route to the internet gateway, and the only thing that ever separated them was that one route.

**2. Security groups are stateful and network ACLs are stateless. Describe a specific USMS request path, name the ports and the direction of each leg, where that difference changes how many rules you must write. Then say which of the two you would reach for first when a new requirement arrives, and why.**

Take a student's browser hitting the web server on port 80. With security groups, I only had to write one inbound rule for TCP 80, the reply going back out is automatically allowed because the group remembers the connection. With my private NACL, I had to write two separate rules for the same kind of traffic pattern, one allowing the actual inbound port, and a second one allowing the whole ephemeral range (1024-65535) just so replies can get back out. Stateless means nothing is remembered between the request and its reply. I would reach for security groups first for any new requirement, since one rule usually covers a full request and reply, and I would only touch NACLs for a subnet wide restriction that has to hold regardless of what any single instance's security group says.

**3. usms-db-sg allows PostgreSQL from usms-app-sg rather than from 10.0.1.0/24. Give two concrete changes to the USMS architecture that would silently break the CIDR-based version while leaving the group-referenced version correct.**

First, if the web tier ever needed to scale into a second subnet, like usms-public-subnet-b, a CIDR-based rule scoped to just 10.0.1.0/24 would silently stop covering the new instances, while a rule sourced from usms-app-sg keeps working since it is not tied to any particular address range. Second, if the app tier ever moved to a completely different subnet, an address-based rule would need to be manually rewritten, but a group-based rule would still be correct automatically, since it just checks group membership, not location.

**4. The NAT gateway sits in usms-public-subnet-a but exists to serve usms-private-subnet-a. Explain why it must be in the public subnet. Then explain what would happen to the private subnet in AZ b if AZ a became unavailable, and what that implies about where the availability boundary really sits.**

It has to sit in the public subnet because it needs its own route to the internet gateway to actually reach the internet, and only the public subnet has that route. If AZ a went down, usms-private-subnet-b would lose outbound internet access too, even though its own instances would be completely fine, because the one NAT gateway serving both private subnets lives in AZ a. That tells me the real availability boundary in this design is not each subnet on its own, it is wherever the NAT gateway happens to be, which is exactly the tradeoff I wrote about in Exercise 4 when deciding whether a second NAT gateway in AZ b was worth the extra cost.

**5. This lab created a gateway endpoint for S3. Describe the path a request from a private instance to usms-student-data takes with the endpoint, and the path it would take without one. Identify which path leaves the AWS network and what that costs in money and in exposure.**

With the endpoint, traffic to S3 travels over a route directly to Amazon's network using a prefix list, never touching the internet gateway or the NAT gateway. Without the endpoint, the same request would have to go out through the NAT gateway to the public internet and come back in to reach S3. That second path leaves the AWS network entirely, which means paying NAT data processing charges for traffic that never needed to go anywhere near the internet, and it also means student data physically crosses a public path instead of staying inside AWS the whole time.

**6. Step 23 restarted Floci and looked the VPC up by tag rather than reusing the VPC_ID shell variable. Explain what specifically would not have been proven had the variable been reused. Relate your answer to the failure described in Lab 1 Step 14.**

If I had just reused $VPC_ID after the restart, all that would prove is that my terminal still remembered a string, not that Floci itself still had the VPC. Looking it up fresh by tag forces an actual API call to Floci's storage, so a correct result only happens if the VPC genuinely survived. This is the same lesson from Lab 1 Step 14, where checking the account root ARN after a restart proved nothing since that value never changes anyway, real persistence has to be proven by creating something, restarting, and looking it up again from scratch.

**7. Floci does not enforce security groups. Given that, explain how you can still be confident that the rules you wrote in Steps 14 and 15 are correct and describe one specific mistake that this lab's verification would catch and one that it would not.**

I can still be confident because I read the actual rule documents back and checked them against what I intended, port numbers, sources, and descriptions, rather than trusting that a command succeeding meant the logic was right. One mistake the verification would genuinely catch is an unattached internet gateway, describe-internet-gateways would show an empty Attachments list even though the gateway itself exists. One mistake it would not catch is whether usms-db-sg's rule actually blocks traffic from anywhere except usms-app-sg, since Floci does not evaluate real traffic against security groups at all, an overly permissive rule and a correctly scoped one would look identical if you only tested by trying to connect to something.
